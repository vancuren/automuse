## CONTRADICTIONS (20)
1. Can hosted SAM 3.1 be called once per frame? Topic 4's summary, Topic 5's risks and Topic 6 say inputs must be uploaded or URL-hosted clips and 'a 5-10 Hz loop cannot call it per frame'. Verifiers on Topics 4, 6, 7 and 10 confirm input_image accepts a base64 data URL, the 50-frame minimum applies only to video requests, and the limit is 3,000 requests per minute. Evidence favours the verifiers: per-frame image calls work. The real limits are unpublished latency and cost ($0.0025 per frame, about $9/h at 1 Hz and $45/h at 5 Hz). Video mode is clip-only and unusable for live control.
2. Can SAM 3.1 run locally on the Mac? Topics 1, 4, 5, 7, 8 and 10 say no (about 1.3 fps through unmerged PyTorch MPS PR #627; the official repo is CUDA-only). Topic 2 found SAM 3.1 merged into mlx-vlm (PR #880, weights at mlx-community/sam3.1-bf16), at about 190-230 ms per frame for 3-5 objects at 1008 px on an M3 Max, plus a 224 px 'realtime' mode at 23-26 fps. Evidence favours Topic 2 that a real local route exists (the verifier confirmed the merge). But all its numbers come from the model card on other hardware, the 224 px mode reuses backbone features up to ~1 s old (bad for a moving camera), and nothing has been run on the M5 Pro. Treat it as an offline fallback candidate that must pass a benchmark.
3. Does Hugging Face transformers support SAM? Topic 7's researcher and Topic 4 say there is no transformers path. Verifiers show transformers ships Sam3Model and Sam3VideoModel (with frame-by-frame streaming) for facebook/sam3, but nothing for SAM 3.1. Even the open 'Add SAM 3.1' PR number differs between topics (#45110 in Topic 1, #46128 in Topic 10); both are unmerged. Evidence: SAM 3 yes, SAM 3.1 no, and MPS speed is unmeasured.
4. Does Baseten host Muse Glimmer? Topic 1's researcher said its library page 404s. Verifiers on Topics 1 and 4 found a dedicated-deployment-only page (BF16 on one H100 with a 2.56B DFlash draft model). Evidence favours the verifiers: it exists, costs about $6.50/h, and has no per-token API.
5. Does Baseten enforce structured output for Muse Spark Open? Topic 1 says it is not supported; Topic 4's docs say the schema is accepted but not enforced; Baseten's library page advertises 'Structured Outputs'. Evidence favours the docs: not enforced, so validate client-side. Related: Topic 4's tool_choice='required' trick works only on Baseten. On the Meta API, tool_choice accepts only 'auto' (Topic 1), so use a strict json_schema there instead.
6. Which host should run the intent LLM? Topics 1, 3, 7 and 8 pick Meta API muse-spark-1.3; Topic 4 picks Baseten Muse Spark Open; the user's text says the model 'can be baseten or fireworks'. The 'Spark 1.3 deprecated in favour of Muse Wonder' label (Artificial Analysis, Topic 1 verifier) is not on Meta's own page: dev.meta.ai/docs/models, fetched today, calls muse-spark-1.3 'the latest version' with no deprecation notice and says Muse Wonder 'is in preview'. Evidence favours Spark 1.3 on the Meta API as the reliable intent parser: enforced strict schema, same key as SAM and voice. The user's wording is permissive, not mandatory, but to honour it the plan should still keep a Baseten- or Fireworks-hosted Muse model (Spark Open serverless or tuned Glimmer) as a switchable path. Spark Open brings an unenforced schema, the -1026 model-ID question, the 'Built with Muse Spark Open' notice and the acceptable-use clause on vehicles.

Topic 1 says there is no Apple-Silicon training path (mlx-lm Glimmer support is text-only and its LoRA unverified). Topics 1 and 4 prefer Fireworks' free managed SFT. Evidence favours Fireworks: verified free until Nov 30, finishes in minutes, accepts image examples. Mac training has no throughput data and competes for the same 48 GB. Local serving of a cloud-trained adapter has an unverified conversion path either way.

Topic 6 says Webots; Topic 1 says MuJoCo (used by Meta's own 14_muse_robotics cookbook, and the only engine verified rendering on this Mac: 1280x720 at ~6.7 ms on a trivial scene, but no human or car assets). 20. What is the SAM output format? Topic 1 and Topic 8's researcher describe positional box tokens (`<|box;x1;y1;x2;y2;w;h|>`). Topic 8's verifier, citing Meta docs, says fields are key=value, w and h are the source frame size (not the box size), c appears only when include_confidence='true', a frame with no match produces no line, and IDs are sparse. The docs win: use meta-sam-parser rather than a hand-written parser.
## TOP_RISKS (10)
1. 1. Deadline and scope blow-up. About 22.5 hours remain (local clock Nov 3 22:31 EST; deadline Nov 4 9:00 PM ET, which is also when the credit claim closes). The dossier's combined scope — voice, LLM, SAM, tracker, controller, twin, real flight, Glimmer LoRA and a GPU SAM server — cannot all fit, and attempting it risks nothing demo-ready. The plan needs hard tiers, hourly go/no-go checkpoints, and submission assets frozen hours before 9 PM.
2. 2. Hosted SAM 3.1 may be too slow or imprecise on attributes, with no proven real-time local fallback. 'Person in blue shirt' may return every person or none. Latency is unpublished (one data point: 1.8 s) and results vary between runs. Local SAM 3.1 (MLX ~0.2-0.5 s per frame expected, PyTorch MPS ~1.3 fps) is unmeasured on the M5 Pro. If p95 latency exceeds ~1.5 s or recall is poor, the follow loop either fails or degrades into an OpenCV demo.
3. 3. Real-flight connectivity on macOS. The drone's access point has no internet, and this Mac has no second uplink configured (only Wi-Fi and Thunderbolt Bridge services). The README's USB Wi-Fi dongle likely has no macOS 26 driver. macOS Local Network permission and network service order can silently block UDP 23458/RTSP to 172.16.11.1 or cut internet. The twin on localhost is immune to all of this, so the classic failure is a twin that works and hardware that is dead on the last day.
4. 4. X69 safety and hardware unknowns. Takeoff, land and flip bits are not confirmed by packet capture, and a wrong bit could flip the drone or cut its motors. Behaviour on RC link loss is unknown. turbodrone's FlightController keeps re-sending the last stick values forever with no staleness check. One-shot commands go out in a single 40 ms datagram. There is no telemetry or battery reading, the loop delay is about 0.6-1 s, and optical-flow drift is likely. A flyaway or crash could injure someone or destroy the only drone before any footage is captured.
5. 5. The twin may not exercise the real perception or dynamics. SAM may not detect synthetic actors, and the twin's dynamics are guesses without system identification. A twin fed ground-truth boxes would hide exactly the SAM latency and attribute risks that sink the real demo. The Webots install may also fail on macOS 26 or break the user's 'stay in this dir' constraint.
6. 6. The fine-tune can eat the day. A Glimmer LoRA means synthetic data generation, Fireworks SFT, then serving the LoRA on a paid H100 ($8/h) with multi-minute cold starts and 503 errors while it scales up. The alternatives are an unverified adapter conversion with no BF16 merge possible in 48 GB, or Mac mlx-lm QLoRA with no benchmarks. It may consume most of the remaining hours and still never be in the live loop.
7. 7. Voice-to-action UX. Muse Spark's reasoning cannot be turned off, so responses take seconds. A solo developer being followed needs a wireless mic while walking, motor noise hurts transcription, and macOS microphone and hotkey permissions must be granted. If 'stop' or 'land' wait on the LLM, or the voice WebSocket is closed for idling, the demo looks broken or unsafe.
8. 8. Environment and dependency friction. opencv-python 5.0 lacks CSRT/KCF, and adding opencv-contrib conflicts with ultralytics. Bare python3 is 3.9.6. omnilingual-asr's PyPI release supports Python ≤3.12 only, and official SAM 3 is CUDA-only. Webots on macOS 26 is unverified, and every install must respect the out-of-dir ban. Each of these can cost hours that this timeline doesn't have.
9. 9. Eligibility, positioning, licensing and secrets. 'New work only' while forking turbodrone can lead to disqualification if the delta is unclear. A person-following drone can read as surveillance. Constraints: the SAM License bans military use, Muse Spark Open's policy restricts vehicle operation, and turbodrone's follow plugin pulls in AGPL ultralytics. A public repo risks leaking .env API keys and draining credits.
10. 10. Running out of credits or budget. The $150 Meta credit must be claimed with a card pre-authorization by the deadline and may cover only some models. Hosted SAM at 5 Hz costs about $45/h, partner credits are discretionary, and an on-demand GPU left running keeps billing. An exhausted key in the middle of recording kills the demo.
## DECISIONS_THE_PLAN_MUST_MAKE (22)
1. Scope tiers for the ~22.5 h window. MVP: twin plus voice, Spark intent, hosted SAM, tracker, controller and a recorded video. Then real X69 flight, then Glimmer LoRA, then GPU or MLX SAM. Each tier needs a timebox, go/no-go checkpoints (e.g. API benchmarks by hour 2, twin closed loop by hour 8, hardware bring-up go/no-go by hour 12) and an asset-freeze time.
2. Project layout under 'don't go outside this dir': a vendored turbodrone fork vs a pinned dependency; one uv venv on Python 3.13 or several (e.g. a 3.12 venv only if fairseq2 Omnilingual is used); redirecting caches and weights (HF_HOME, UV_CACHE_DIR, ./models); secrets in a gitignored .env; keeping turbodrone's Apache-2.0 LICENSE and NOTICE.
3. How deeply to integrate turbodrone: (a) a SamFollowPlugin inside a turbodrone fork; (b) a new orchestrator that imports only the x69_lg RC and video protocol modules; or (c) unmodified turbodrone driven over REST/WS. In every case decide whether to delete the AGPL ultralytics/YOLO follow plugin and switch to opencv-contrib-python.
4. Process and messaging layout: separate processes or threads for voice/agent, perception, controller with the 25 Hz RC sender, twin, and UI; the messaging layer between them (WebSocket, ZeroMQ, shared memory or REST); a mailbox that always holds only the newest frame instead of the 100-deep queue; and frame timestamps.
5. Video input path: turbodrone's FramePump JPEGs (re-encoded at quality 85, 100-deep queue) or decoding RTSP directly with OpenCV/PyAV in the perception process. RTSP or the H.265 UDP mode as default. The resolution sent to SAM (640x360 vs native).
6. Detector setup and fallback order: hosted sam-3.1 image calls (rate, resolution, number of requests in flight, budget limiter) vs local SAM 3.1 via MLX (needed for offline flight) vs a self-hosted GPU SAM on Baseten or Modal (stretch, or drop it). Hosted video mode used only for offline labelling and regression tests.
7. Tracker between detections: opencv-contrib CSRT/KCF, VitTrack (with its ONNX file), Meta's EdgeTAM/EfficientTAM, SAM 3.1 MLX track_step, or a Kalman filter alone. The choice depends on how strict 'all Meta models' is. Also decide IoU thresholds for matching, re-anchoring, and when a target counts as low-confidence or lost.
8. Picking the right target: normalise the phrase to SAM-friendly form (one concept, at most two attributes); resolve multiple candidates by HSV colour on the mask, by Spark or Glimmer vision on numbered crops, or by Spark grounding boxes; hover until the target is confirmed; lock its identity; and ask the user to clarify when there are zero or ambiguous matches.
9. Intent layer: muse-spark-1.3 on the Meta API (minimal/low reasoning, strict json_schema, tool_choice only 'auto') vs muse-wonder-1.0 (preview) vs Spark Open on Baseten or Fireworks (tool call plus Pydantic validation) vs base or tuned Glimmer via llama-server json_schema. Also: which is primary and which fallback, the intent schema, a one-shot parser vs an agent tool loop (Best Agentic bonus), a local keyword fast path for stop/land, and clarification turns via previous_response_id.
10. Training deliverable: a Glimmer LoRA distilled for intent parsing. Decide the data teacher (Spark or Wonder; standard vs contributor tier), the training venue (Fireworks free SFT, Baseten Training or Mac mlx-lm), the eval set and metrics, and how it is served (a Fireworks on-demand window vs local base model only). Or explicitly go prompt-only if the timebox expires. Explicitly drop SAM detector fine-tuning and behaviour cloning.
11. Controller design: which axes are autonomous (yaw and pitch; vertical framing by throttle or by camera-tilt pulses; roll at 0); the control law (plain P with deadbands vs PD with target-velocity feed-forward and a Smith-style predictor); gains derived from measured total loop delay; caps and slew limits; speed tier 0; controller rate vs the 25 Hz RC rate (keep CONTROL_RATE or change it).
12. Safety architecture: a SafetyGovernor at the FlightController choke point; zero sticks when commands go stale; a frame-age watchdog; a dead-man key; hover-then-land escalation timers; repeating one-shot flags over several packets; motor-cut e-stop (0x02) only by a human hotkey at low altitude; a battery timer; manual input overriding autopilot; turbodrone's 'any keypress kills the plugin' behaviour; and what the drone receives if a process crashes.
13. Voice front end: Muse Voice Transcribe in push-to-talk or endpointing mode; capture in the browser and proxy through the backend (keeps the API key off the client) vs Python sounddevice; one session per utterance vs a persistent one; the keyword-bias list; an offline fallback (sherpa-onnx Omnilingual on 3.13, or none); spoken feedback (none, MMS-TTS or macOS `say`).
14. Twin engine and actors: a pip/npm-only engine (MuJoCo, a Python/OpenCV/pyrender kinematic renderer, or Three.js) vs Webots (system install). Actor assets: procedural, CC0 glTF, Muse Image billboards or real-footage sprites, chosen by a SAM-detectability test. The canned scenario list.
15. How the twin connects and how faithful it is: in-process sim adapters vs a network-level emulator (UDP 23458 parser plus RTSP via mediamtx/ffmpeg, using the DRONE_IP and X69_LG_RTSP_URL overrides) — and which one is the acceptance test. Dynamics model and where its parameters come from (guessed vs measured). How much latency, noise and frame drop to inject. A mock SAM using ground-truth boxes vs real-SAM test modes, plus metrics and pass thresholds that define a 'complete digital twin'.
16. Network setup for real flights: Wi-Fi on the drone's access point with iPhone USB tethering or USB-C Ethernet for internet (service order, Local Network permission), vs a fully local in-flight stack, vs cloud models used only in the twin.
17. UI: extend turbodrone's React UI (overlay types for masks and state, transcript and intent JSON, latency bars, a dead-man/kill control, the hard-coded localhost:8000) or build a minimal new dashboard. Decide what appears in the demo video.
18. Demo and submission: video structure (twin first, real flight if available, honest labelling of which is simulated); whether to host a live twin, and if so how keys and cost are protected; the README list of models used; showing new work clearly (fresh git history, disclosure of the fork); the optional X post.
19. Hackathon framing and compliance: Indie or Startup track, the 'Push the Frontier' theme, a consumer follow-me camera framing, targeting by attributes only (never identity), and required licence and attribution files (SAM License for meta-sam-parser and any weights; Muse Spark Open's 'Built with Muse Spark Open' notice if used; CC-BY-NC if MMS-TTS is used).
20. Cost controls: client-side limits on SAM calls per minute and spend per session, a spend cap on dev.meta.ai, when on-demand GPUs scale to zero vs keep a replica, and which pricing tier generates synthetic training data.
